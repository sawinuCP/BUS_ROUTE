# 11 — Backend API Design

Base path: `/api/v1`. JSON over HTTPS. Use OpenAPI generated by FastAPI.

## Public endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/places/search?q=` | Search places and aliases |
| GET | `/places/{place_id}` | Place details/access points |
| GET | `/stops/search?q=&mode=` | Search stops/stations |
| GET | `/stops/{stop_id}` | Stop and access point details |
| POST | `/journeys/plan` | Generate multimodal itineraries |
| GET | `/journeys/{journey_id}` | Retrieve saved/session plan |
| POST | `/journeys/{journey_id}/refresh` | Re-plan against active dataset |
| POST | `/journey-sessions` | Start active journey |
| POST | `/journey-sessions/{id}/events` | Confirm boarding/alighting/progress |
| POST | `/journey-sessions/{id}/replan` | Re-plan active session |
| POST | `/reports` | Submit data issue (consent-gated, idempotent) |
| POST | `/ai/explain-step` | Grounded step explanation (AI or built-in fallback) |
| POST | `/ai/why-route` | Grounded "why this route?" explanation (same contract) |
| GET | `/preferences` | Read user preferences (accounts; local-first until then) |
| PUT | `/preferences` | Update user preferences (accounts; local-first until then) |

## Internal/admin endpoints

```json
  "generated_at": "2026-11-19T08:00:00Z",

  "options": [

      "id": "option-1",
      "summary": {
        "estimated_duration_minutes": {"min": 55, "max": 75},
        "walking_distance_m": 640,

      },
      "warnings": ["Service operation has not been checked in real time"],

          "from": "origin",
          "to": "stop-access-1",

        },
        {
          "type": "transit",
          "mode": "bus",
          "route_id": "route-id",
          "pattern_id": "pattern-id",
          "board_access_point_id": "access-1",
          "alight_access_point_id": "access-2",
          "instruction_code": "RIDE_TRANSIT"
        }
      ]
    }
  ],
  "notes": ["No journey found within the given constraints."],
  "suggestions": [
    {
      "kind": "nearby_stop",
      "role": "origin",
      "text": "Alternative mapped stop for the origin: X halt — 220 m away (straight-line as mapped; walking distance not checked).",
      "stop_id": "stop-id",
      "stop_name": "X halt",
      "distance_m": 220
    },
    {
      "kind": "larger_walk_cap",
      "role": "request",
      "text": "Re-plan with max_walking_m ≥ 4400 m — the routed walking-only distance is 4219 m.",
      "suggested_max_walking_m": 4400
    }
  ]
}
```

A `no_route` response may carry **adjustment suggestions** (Phase 7 item 6).
Every suggestion is derived from canonical mapped data (mapped stops,
straight-line distances always labelled "as mapped") or from a distance the
walking engine actually routed; a suggestion never claims a service,
timetable or fare and never asserts that the alternative works — the client
re-plans through the same endpoint and the planner answers honestly again.
An `ok` response carries no suggestions.

Recovery flows (Phase 7 item 5) reuse the session endpoints: the traveller
**confirms** the stop they are actually at (never auto-detected), and
`POST /journey-sessions/{id}/replan` re-plans with an optional `origin`
override; when nothing connects it answers `replanned: false` with reasons
and leaves the session untouched.

## Reports and moderation (Phase 7 items 4, 7, 8)

`POST /reports` is **append-only and idempotent**: the client generates a
stable `client_key` (kept across offline-queued retries), and resubmitting
the same key returns the existing report (`duplicate: true`) instead of
creating a second one. **Explicit consent is required** — `consent: false`
is rejected with 400 and nothing is stored; the consent is recorded on the
row. Categories (plan item 7): `wrong_stop`, `route_variant`, `direction`,
`transfer_path`, `landmark_name`, `fare`, `access_attribute`,
`outdated_data`, `other`. A report is tied to canonical entities (stop,
route, pattern, transfer, journey) and the dataset version it was made
against — **never to coordinates**.

Moderation (item 8) lives on the admin router (mounted only outside
production; OAuth2/OIDC + RBAC land in Phase 9):
- `GET /admin/reports?status=` — triage queue, oldest first.
- `POST /admin/reports/{id}/review` with `accept | reject | needs_info`:
  acceptance records a new **candidate** dataset version
  (`field-reports-<report id>`, status `candidate`) for the ingestion
  pipeline — it is **never auto-published** and the active dataset is
  untouched; rejection and needs-info change nothing outside the report row.
  Accepted/rejected reviews are terminal; `needs_info` can be reviewed again.

## Grounded AI assistance (Phase 8 items 1–3, 6–8)

`POST /ai/explain-step` and `POST /ai/why-route` add **optional**
comprehension help on top of the deterministic planner. The contract:

- **Request**: exactly one of `journey_id` (saved-journey snapshot fetched
  server-side — preferred) or `journey` (inline plan-response snapshot,
  e.g. from the offline cache); `option_index` (default 0);
  `step_index` (required for `explain-step`).
- **Response** (always 200):
  ```json
  {
    "mode": "explain_step",
    "source": "ai | deterministic_fallback",
    "provider": "openai_compatible | null",
    "model": "<configured model> | null",
    "explanation": "...",
    "cites": ["f_step", "f_summary"],
    "dataset_version": "...",
    "notes": ["..."],
    "language": "en"
  }
  ```
- **Grounding contract (items 2, 6)**: the provider sees **only** a
  self-contained facts bundle built from the selected option — summaries,
  labels, warnings, notes and step facts with **all coordinates stripped**
  (privacy filter, item 8). The model must answer in strict JSON and cite
  fact IDs from the bundle; the response is rejected (→ fallback) when it
  cites unknown fact IDs, mentions a route code absent from the facts, or
  contains a fare/price, clock time or service frequency — the AI cannot
  add a route number, stop, direction, fare, service time or landmark not
  present in the supplied facts.
- **Deterministic fallback (item 7)**: provider outage, timeout,
  misconfiguration, rate limiting, disabled deployment (`AI_EXPLANATIONS_ENABLED=false`,
  `AI_PROVIDER=none`) and ungrounded output all answer 200 with
  `source: "deterministic_fallback"` — the same templates the instruction
  engine uses. AI is optional and never required for a valid itinerary.
- **Prompt-injection guard**: the system prompt declares the facts block
  untrusted data (instruction-like text inside it must be ignored); a model
  that "obeys" injected text produces ungrounded content which validation
  rejects (covered by tests).
- **Provider factory (item 1)**: adapters are selected by configuration —
  `AI_PROVIDER` (`none` | `openai_compatible`) with `AI_BASE_URL`,
  `AI_MODEL`, `AI_API_KEY` (secret: environment only), `AI_TIMEOUT_SECONDS`,
  `AI_MAX_OUTPUT_TOKENS`. Any OpenAI-compatible chat endpoint works; the
  domain code depends on no LLM SDK. A simple per-client sliding-window
  throttle (`AI_REQUESTS_PER_MINUTE`) guards cost; real rate limits land in
  Phase 9.
- **Explanations are English-only** until native review (D-7); the response
  carries the `language` and honesty notes ("follow the step instructions").

## Admin authentication and hardening (Phase 9)

- **Admin endpoints** (`/admin/*`) require the operator bearer token:
  `Authorization: Bearer <ADMIN_API_TOKEN>` (secret, environment only —
  never committed). Wrong/missing → 401 `UNAUTHORIZED`; the attempt is
  audit-logged without the presented credential.
- **Fail-closed default**: with `ADMIN_API_TOKEN` unset, admin requests are
  refused with 403 in `staging`/`production` — an unconfigured deployment
  can never serve admin endpoints. Only `local`/`test` may run in dev mode
  (the router is only mounted there anyway). OAuth2/OIDC + RBAC replace the
  single-operator token when identity exists (doc 14).
- **Audit logging**: every data-changing admin action (source create/sync,
  dataset publish/rollback, verification create, report review) emits a
  structured `admin_audit` JSON log line with request id, client, action,
  entity and outcome — no tokens, bodies or credentials. Publish/rollback
  and report-review audit trails are a doc 14 requirement.
- **Rate limiting**: the shared platform limiter (`app.platform.rate_limit`)
  throttles per client: report submissions (`REPORT_RATE_LIMIT_PER_MINUTE`,
  429 `RATE_LIMITED`) and AI calls (`AI_REQUESTS_PER_MINUTE`). It is
  in-process and single-node; a multi-node deployment must back it with
  Redis or an edge proxy (release-checklist item).
- **Security headers** on every response: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Cache-Control: no-store`. HTTPS/HSTS terminates at the reverse proxy.

## Local-first data and privacy (Phase 7 item 10)

- **Saved journeys**: anonymous (no account), stored server-side as the exact
  request + response snapshot, retrievable/refreshable by UUID only — no
  personal data beyond the chosen stops; deletion is available on request
  via the operator (retention note in the data model doc).
- **User preferences**: local-first on the device (SQLite) until accounts
  exist; the `GET/PUT /preferences` endpoints are reserved for the
  account-sync decision (plan item 10) and are not used by the app today.
- **Offline caches and queues** (plan cache on the steps screen, offline
  progress events, queued reports): device-only, never location data; queued
  progress events and reports are reconciled idempotently against the
  backend and never change canonical data by themselves.
- **Active journey sessions**: no location data stored on sessions or events;
  GPS on the device is assistive-only and any single-fix use (the recovery
  "stops near me" search) is explicit, transient, and never persisted.

## API design rules
- Use stable internal IDs; expose source IDs only when appropriate.
- Validate request schemas and bound coordinate/radius inputs.
- Include request ID, dataset version and warnings.
- Separate network feasibility from live availability.
- Use pagination for administrative/search lists.
- Use idempotency keys for report/session creation where needed.
- Return consistent error shape: code, message, details, request ID.
- Rate-limit public endpoints and protect admin endpoints.
- Never return provider credentials or raw restricted payloads.
